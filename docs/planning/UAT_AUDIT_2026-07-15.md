Hampir semua expected value di 96 fixture YAML sudah **kadaluarsa**. Database telah berubah secara signifikan sejak fixture ditulis. Dari 45+ nilai yang diverifikasi langsung ke DB, hanya 1 yang cocok persis (UAT-TREN-ERBA-2023 = 42.329).

**Temuan utama:**
1. **98% expected value tidak cocok dengan DB saat ini** — range discrepancy dari +0.006% sampai +282%
2. **Agent SQL sering sudah benar** — banyak "failure" sebenarnya agent menghasilkan angka yang benar berdasarkan DB saat ini
3. **Filter code MASIH bermasalah di beberapa skenario** — terutama pipeline status codes dan jenis_permohonan
4. **`data_dictionary` tidak punya mapping terstruktur** untuk pipeline stages → status codes

4. **Filter code 0999 vs 3-status** masih menjadi masalah di RISIKO-4-KATEGORI dan RISIKO-TINGGI-NOTIF
5. **`data_dictionary` tidak punya mapping pipeline** yang terstruktur
6. **`klasifikasi_id` adalah kolom deprecated** — tidak boleh dipakai untuk query baru
7. **Komitmen perlu `ROUND()` normalization** — ada representasi integer dan decimal ('5' vs '5.0')
8. **Metodologi COUNT mempengaruhi hasil** — `COUNT(*)` vs `COUNT(DISTINCT nomor)` vs `COUNT(DISTINCT produk_id)` menghasilkan angka berbeda

### Rekomendasi

1. **Regenerasi semua fixture** dari DB saat ini dengan SQL yang benar (`COUNT(DISTINCT nomor)` + test account exclusion)
2. **Gunakan tolerance-based assertion** (`assert_any_of` + `tolerance_pct`) untuk semua nilai numerik
3. **Tambah kategori `STATUS_GROUP`** di `data_dictionary` untuk mapping pipeline
4. **Perbaiki filter code** untuk skenario yang memang salah (COM-2, RISIKO 0999 vs 3-status)
5. **Dokumentasikan definisi "aktif"** yang kanonik per skenario (0999-only vs 3-status)
6. **Ganti `klasifikasi_id`** dengan alternatif filter via `nama_kategori` string discovery
7. **Gunakan `ROUND(status_komitmen::numeric)::int::text`** untuk query komitmen
8. **Terapkan aturan COUNT method** — `COUNT(DISTINCT nomor)` untuk NIE, `COUNT(DISTINCT produk_id)` untuk permohonan, `COUNT(*)` hanya untuk tabel master
